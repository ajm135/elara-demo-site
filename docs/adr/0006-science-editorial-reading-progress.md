# 0006: Science-editorial page layout and header-only reading progress

- Status: accepted
- Date: 2026-10-18

## Context

Milestone 3 redesigns the five existing pages from a flat stack (nav label as a paragraph, heading, summary, bare images, sections, disclaimer) into a composed, contemporary light science-editorial experience for general readers. The companion record `0006-editorial-design-system.md` covers the token palette, local type, and the progress helpers in the content model; this ADR covers how those tokens are applied to the shared chrome and the page composition, and how the header orients readers to their place in the five-story sequence.

Two constraints shaped the current-page detection decision. First, the site is static: every route is prerendered from `src/lib/site-content.ts`, so a `headers()` call in the shared chrome would opt every route out of static rendering (and `headers()` is unavailable during build-time prerender at all). Second, this was verified against a live Next 16.4 server on this computer: in a server component, `headers()` exposes only the incoming browser headers (user-agent, host, forwarding headers) — the request path is not among them — and Next strips its internal `next-url` header for non-interception routes before rendering. No server-only request API available in this project can read the request path on the initial render.

## Decision

- The shared chrome is `src/components/site-header.tsx`, a server component (no `use client`) rendered by each route's page, not by the root layout: each of the five `src/app/.../page.tsx` files renders `<SiteHeader currentPath={page.path} />` immediately before its `<StoryPage page={page} />`. A route is a static server component that already knows its own path, so the server always knows the current page; this is the deterministic, testable equivalent of a request-API read. `src/app/layout.tsx` no longer renders the header (a shared layout cannot know which child page is being rendered) and keeps only the document, fonts, and metadata. The path-to-page mapping is the pure helper `sitePageForPath(path)` in `src/lib/site-content.ts`, so Node tests resolve paths without a browser or request simulation.
- Keyboard order on every page is: the skip link (class `skip-link`, `href="#main-content"`, visible text "Skip to main content", the first focusable control), then exactly one `<header>` containing exactly one `<nav aria-label="Main">` with the five story links in `sitePages` order and no other links before or between them, then the progress cue. The header marks exactly one link with `aria-current="page"` — the current story's — and the other four links never carry it.
- The active treatment is not colour alone: `globals.css` styles `nav a[aria-current="page"]` with a heavier weight and an inset accent rule in addition to the always-present underline, so the current story is identifiable without colour.
- Inside the same header, after the nav, the reading progress renders as a plain paragraph (`.progress-cluster`), not a second navigation: the exact position label from `storyPositionLabel` ("Story 1 of 5" through "Story 5 of 5"), and either a next-story cue (a link to the next story's path with its nav label, stories 1 to 4) or, on story 5 only, the visible ending state "End of the stories" with no next link. The cue never places a link ahead of the five story links in keyboard order.
- The skip target is focusable without entering the tab sequence: `src/components/story-page.tsx` renders the single `<main id="main-content" tabindex="-1">`. There is exactly one main landmark per page, and nothing inside main is a navigation.
- Each story is a composed hero (`.hero`): the story's nav label as a kicker, the single `<h1>`, the summary, and the page's real review date as a visible "Stories reviewed …" line carrying `<time datetime="2026-10-18">` (the date every cited source was actually inspected; see ADR 0005 and `docs/runbooks/content-evidence.md`), with the page's illustration in a framed figure (`.hero-media`: raised surface, meaningful rule). At 768px and up the text sits beside the framed image; below 768px the hero stacks. A page's further illustrations (the cancer story ships two) render as framed figures (`.story-illustration`) after the hero. All images stay native `<img>` with the existing src, alt, width, and height; alt text stays non-empty and descriptive; nothing is remote.
- After the hero, sections render as `<h2>` plus plain paragraphs, with each `ClaimEvidence` panel (unchanged `figure.claim-evidence` / figcaption / ul / cite / a structure) immediately after the paragraph that makes the claim and still inside that section, styled by the existing evidence-panel rules. Long-form copy stays inside the 60–75 character measure set by the `--measure` token on `main`; the warm surfaces, dark ink, and restrained teal accent come from the tokens in `0006-editorial-design-system.md`. The per-page disclaimer stays a plain paragraph and the last element of main, and still contains the visible text "not medical advice".
- The longevity story's "Three numbers, three different things" section additionally renders its three distinctions as exact, visible term labels so a reader can find them without reading the paragraphs: the static section model gains an optional, ordered `terms` list of term/definition pairs (used only by that page), and `story-page.tsx` renders it as `<dl class="lifespan-terms">` right after the section's h2, with each `<dt>` set to exactly "Life expectancy", "Maximum lifespan", or "Healthy lifespan" in reading order and each `<dd>` one short plain-language definition taken from the meaning the adjacent paragraphs already carry (a population average of years expected at birth; the longest individual human life observed, not a population forecast; the proportion of life spent in good health). No future lifespan number, cure, or researcher attribution is introduced. The cited claim sentences — including the healthy-lifespan sentence the evidence register tracks — remain exact substrings of their paragraphs, so `claimsForParagraph` and the evidence panels still attach to the unchanged copy, and the heading hierarchy (one h1, h2 only), the header-only navigation, and the disclaimer's position are untouched. `globals.css` styles the list from the existing tokens only: dark ink on the evidence surface (4.5:1 pairs the token test already verifies), terms not colour-only, no text-transform, no required animation, and no min-width above 320 px.
- Essential reading works with JavaScript disabled: everything above is server-rendered HTML with no required animation, no deferred content, and no client-side menus.
- The home page is the one page that makes no consequential claim of its own, so it would otherwise ship no openable citation link in `main` while the four story pages carry them via their evidence panels. Rather than attach a claim the home copy does not actually make, the home page data carries an optional sources block (heading, short intro, and the complete `referenceCatalogue` id list in catalogue order), rendered by `story-page.tsx` as `section.sources` after the reading map and before the disclaimer: one list item per catalogue entry with the same title / publisher / date / stable-https-or-DOI anchor shape the evidence panels use, resolved by the pure helper `resolvePageSourceReferences`. Every route therefore carries at least one external citation link in `main` (the check `main a[href^='https://']` in `tests/e2e/reading-experience.json`), the evidence trail starts at the front door, and no new claim or source is introduced. `docs/runbooks/content-evidence.md` records where the sources appear on the pages.

## Notes

- This ADR does not claim completed WCAG 2.2 AA conformance or cross-browser verification. The contrast and structure safeguards run in Node against the design tokens and the rendered source; actual browser behaviour (skip-link focus, zoom, reflow, screen-reader navigation, and the four supported browsers on phone, tablet, and desktop) remains the explicitly documented verification gap carried from the innovation review and ADR 0004, to be exercised by Elara's browser checks defined in `tests/e2e/reading-experience.json`.
- `npm run verify:reading` (`scripts/verify-reading.mjs`) is a Node-only *definition* check, added by this milestone for the next milestone's reading checks: it reads `tests/e2e/reading-experience.json` and verifies that file is complete (the five routes, the required selectors, the "AI and longer lives" title and exact "Story N of 5" progress strings, the story-five ending state, the skip-link steps, and the explicit unverified-gap list). It starts nothing — no server, no socket, no browser — and it performs no browser-level check of its own. Actual browser behaviour remains Elara's page checks against the loopback production server, and stays an explicitly documented verification gap, not a completed WCAG 2.2 AA conformance claim.
- Where the older source-level tests still expect the pre-redesign markup — the nav label as the first plain paragraph of main, the unclassed `<main id="main-content">` opening tag, or unclassed anchors — those assertions are the exact-markup expectations this milestone replaces with the semantic safeguards above (one `aria-current`, a focusable skip target, labelled progress). Updating those tests is the next task in this milestone; no accessibility requirement is skipped or weakened.
- Tests: `tests/story-progress.test.ts` (position labels, next-story helper, ending, `sitePageForPath`, review dates), `tests/design-tokens.test.ts` and `tests/accessibility-essentials.test.ts` (token-computed contrast, focus, measure), and the route/story tests (landmarks, headings, images, evidence, metadata).
